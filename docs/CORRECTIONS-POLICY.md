# Corrections Policy

PostalMind AI will correct factual errors. This page states how, so a correction is a visible,
dated event — never a silent edit.

## The rule

**PostalMind never silently rewrites an important factual claim.** If a claim on `/ground-reality`, in
`content/linkedin/`, or in a published `/evidence` case turns out to be wrong, incomplete, or
misattributed in a way that matters, it is corrected in place **and** logged at `/corrections` with:

- **Original claim** — the exact wording that was published.
- **Corrected claim** — the exact wording that replaces it.
- **Reason** — why it changed (new source, source re-checked and found inaccurate, a category error
  such as attributing a departmental case to GDS, a reader-reported error, etc.).
- **Date** — when the correction was made.
- **Source** — what the correction is based on.

A correction is logged even when it makes the project's own prior post look worse, and even when
nobody outside the project has noticed the error yet.

## What counts as "important"

Any factual claim that could change what a reader concludes: a source misattributed, a date wrong, a
quote inaccurate, a source class overstated (e.g. a blog treated as a primary document), a causal claim
that should not have been made, or a case wrongly categorised (for example, a departmental officer's
case described as a GDS case). Typo fixes, formatting, and non-substantive wording changes are not
logged as corrections.

## What is never done

- A published factual error is never quietly deleted or edited without a corresponding entry at
  `/corrections`.
- A correction never itself introduces a new unsupported claim to explain away the original error.
- A correction to one post never gets buried only in that post's file history — it is also visible at
  `/corrections`, in one place, dated.

## Process

1. An error is identified (self-caught, reader-reported, or found during a later verification pass).
2. The claim is re-checked against its source, or a better source if the original was insufficient.
3. The content is corrected in place.
4. An entry is added at `/corrections` with all five fields above.
5. If the error was significant enough to change a published classification (e.g. UNVERIFIED →
   VERIFIED, or a case wrongly attributed to GDS), the correction entry says so explicitly.

## Reporting an error

Open an issue on the repository, or use the reporting channel described in `SECURITY.md` for anything
sensitive. Include what you believe is wrong, and — if you have one — the source that shows it.
